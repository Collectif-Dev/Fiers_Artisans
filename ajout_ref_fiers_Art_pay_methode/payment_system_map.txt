Systeme de paiement manuel - Wave / Mobile Money (CI)
Carte metier synchronisee avec le code actuel du projet Fiers Artisans

Source de verite detaillee :
- DOCUMENTATION_PAIEMENT_MANUEL.md

1. Vue d'ensemble
- Mode actif : paiement manuel Mobile Money
- Wave API : conservee, mais le flux principal reste manuel
- Abonnement : 5 000 FCFA / mois
- Validation : humaine cote admin
- Temps reel : mobile + admin

2. Cycle nominal
1. L'artisan initie une demande
   - creation ou reutilisation d'une transaction
   - statut initial : PENDING
2. L'artisan paie hors systeme
   - Wave manuel / Orange Money / MTN / Moov
3. L'artisan envoie une preuve
   - capture ecran
   - numero expediteur
4. Le backend valide la preuve
   - transaction existante
   - hash image unique
   - format image autorise
   - sender_number coherent
5. L'admin traite
   - validation
   - rejet
   - reouverture limitee
6. Le backend synchronise
   - transaction
   - abonnement
   - notifications
   - temps reel

3. Etats persistants
- PENDING
- PENDING_ADMIN
- COMPLETED
- REJECTED
- EXPIRED

4. Etats metier derives
- REJECTED simple
  - validated_at = null
  - meme transaction reutilisee
- REJECTED apres validation
  - validated_at != null
  - abonnement desactive si encore actif
  - transaction historique
  - prochaine demande = auto-remplacement
- EXPIRED remboursement en attente
  - refund_required = true
  - refund_done_at = null
  - toute nouvelle demande bloquee
- EXPIRED remboursement traite
  - refund_done_at != null
  - nouvelle transaction creee automatiquement a la reprise

5. Regles critiques
- Toujours raisonner sur la derniere transaction reelle
- Ne jamais creer un doublon si une transaction PENDING ou PENDING_ADMIN existe deja
- Un REJECTED simple reste sur la meme transaction
- Le cooldown ne cree jamais un nouvel ID
- Un REJECTED apres validation precedente cree un nouveau cycle
- Un EXPIRED non rembourse bloque strictement toute nouvelle demande
- request_number augmente de facon monotone par abonnement
- Toute transaction remplacee conserve la trace vers le nouvel ID

6. Rejet et cooldown
- Le cooldown concerne le rejet simple avant validation precedente
- Base : 5 heures
- Progression : 5h -> 10h -> 20h -> ...
- Pendant le cooldown :
  - sender bloque
  - upload image bloque
  - soumission bloquee
  - meme transaction conservee

7. Expiration et remboursement
- Le cron expire les PENDING_ADMIN hors delai
- Si abonnement actif :
  - desactivation avec raison TRANSACTION_EXPIRED
- Puis :
  - status = EXPIRED
  - refund_required = true
  - notification artisan
  - evenement temps reel admin
- Tant que refund_done_at est null :
  - aucune nouvelle demande autorisee

8. Auto-remplacement
Cas eligibles :
- REJECTED apres validation
- EXPIRED avec remboursement deja traite

Effets :
- creation d'une nouvelle transaction PENDING
- reutilisation du previous_provider
- incrementation de request_number
- lien historique via replaced_by_transaction_id
- notification PAYMENT_MANUAL_AUTO_REPLACED
- evenement timeline + temps reel admin

9. UI artisan
- PENDING :
  - sender actif
  - bouton principal bloque
- PENDING_ADMIN :
  - sender bloque
  - preuve bloquee
- REJECTED simple :
  - motif visible
  - meme ID
  - cooldown visible si actif
- EXPIRED remboursement en attente :
  - bloc rouge dedie
  - bouton WhatsApp
  - nouvelle demande interdite
- REJECTED apres validation / EXPIRED rembourse :
  - bascule automatique vers un nouvel ID

10. UI admin
- Scope ACTIVE :
  - PENDING
  - PENDING_ADMIN
  - COMPLETED
  - REJECTED simples non archives
- Scope HISTORY :
  - EXPIRED
  - REJECTED apres validation
  - transactions remplacees
- Actions interdites sur historique :
  - validate
  - reject
  - reopen

12. Invariant de securite
- un abonnement actif doit rester coherent avec une transaction valide
- une transaction historique ne doit plus etre mutable
- aucune demande nouvelle si remboursement en attente
- aucune duplication de transaction PENDING pour un meme abonnement
