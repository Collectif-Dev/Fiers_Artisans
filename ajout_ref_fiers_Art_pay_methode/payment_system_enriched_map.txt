3. Etats persistants
- PENDING
- PENDING_ADMIN
- COMPLETED
- REJECTED
- EXPIRED

4. Etats derives
- REJECTED simple
  - status = REJECTED
  - validated_at = null
- REJECTED apres validation
  - status = REJECTED
  - validated_at != null
- EXPIRED remboursement en attente
  - status = EXPIRED
  - refund_required = true
  - refund_done_at = null
- EXPIRED remboursement traite
  - status = EXPIRED
  - refund_done_at != null
- Historique archive
  - EXPIRED
  - REJECTED apres validation
  - replaced_by_transaction_id != null

5. Initiation
Entree :
- POST /api/v1/payments/manual/initiate

Resolution :
1. verifier provider disponible
2. resoudre l'artisan et l'abonnement
3. bloquer si abonnement deja actif
4. charger la derniere transaction reelle
5. appliquer la matrice suivante

Matrice :
- PENDING
  - retourner la meme transaction
- PENDING_ADMIN
  - retourner la meme transaction
- REJECTED simple
  - retourner la meme transaction
- remboursement en attente
  - erreur PAYMENT_MANUAL_REFUND_PENDING
- REJECTED apres validation
  - creer un nouvel ID automatiquement
- EXPIRED remboursement traite
  - creer un nouvel ID automatiquement
- aucun historique coherent
  - creation normale

6. Auto-remplacement
Declencheurs :
- REJECTED apres validation
- EXPIRED avec remboursement deja traite

Effets backend :
- nouvelle transaction PENDING
- previous_provider reutilise
- request_number = precedent + 1
- ancienne transaction.replaced_by_transaction_id = nouvel ID
- timeline : PAYMENT_MANUAL_AUTO_REPLACED
- notification : PAYMENT_MANUAL_AUTO_REPLACED
- SSE admin : PAYMENT_MANUAL_TIMELINE_UPDATED

7. Soumission de preuve
Entree :
- POST /api/v1/payments/manual/:transactionId/submit-proof

Controles :
- ownership
- status autorise : PENDING ou REJECTED simple
- cooldown_until absent ou depasse
- hash image non duplique
- fichier image valide
- sender_number valide

Effets :
- creation payment_proof
- status -> PENDING_ADMIN
- reset cooldown actif

8. Validation admin
Entree :
- PATCH /api/v1/admin/payment-proofs/:id/validate

Effets :
- status -> COMPLETED
- validated_at renseigne
- activation abonnement
- notification PAYMENT_MANUAL_VALIDATED
- push / temps reel

9. Rejet admin
Entree :
- PATCH /api/v1/admin/payment-proofs/:id/reject

Branche A - rejet simple
- transaction en cycle normal
- validated_at = null
- status -> REJECTED
- motif enregistre
- cooldown progressif tous les 3 rejets du cycle
- notification :
  - PAYMENT_MANUAL_REJECTED
  - ou PAYMENT_MANUAL_COOLDOWN

Branche B - rejet apres validation
- validated_at != null
- status -> REJECTED
- abonnement desactive si actif
- raison : TRANSACTION_REJECTED
- aucun cooldown pour reutiliser la meme transaction
- transaction archivee
- prochain chargement / initiate = auto-remplacement

10. Cooldown
Champs :
- cooldown_until
- cooldown_cycle

Formule :
- 5h * 2^(cycle - 1)

Exemples :
- cycle 1 = 5h
- cycle 2 = 10h
- cycle 3 = 20h

Effets UX :
- sender bloque
- upload bloque
- bouton de soumission bloque
- temps restant affiche en temps reel

11. Expiration
Traitement cron :
- selection des PENDING_ADMIN hors delai

Effets :
1. si abonnement encore actif :
   - deactivateSubscription(reason = TRANSACTION_EXPIRED)
2. status -> EXPIRED
3. refund_required = true
4. attempted_refund_count + 1
5. timeline PAYMENT_MANUAL_EXPIRED
6. notification PAYMENT_MANUAL_EXPIRED
7. SSE admin timeline updated

12. Remboursement
Entree :
- PATCH /api/v1/admin/payment-proofs/:id/mark-refunded

Effets :
- refund_done_at renseigne
- refund_required = false
- timeline REFUND_PROCESSED
- notification REFUND_PROCESSED
- transaction reste historique
- prochain initiate peut auto-remplacer si EXPIRED

13. Reouverture admin
Autorisee uniquement pour les transactions encore coherentes avec un cycle actif.

Interdit sur :
- EXPIRED
- REJECTED apres validation
- transaction deja remplacee

14. Filtres admin
GET /api/v1/admin/payment-proofs

Scopes :
- ACTIVE
- HISTORY
- ALL

ACTIVE :
- PENDING
- PENDING_ADMIN
- COMPLETED
- REJECTED simples non archives

HISTORY :
- EXPIRED
- REJECTED apres validation
- transactions remplacees

16. Scenarios de reference
Scenario A - nominal
- PENDING -> PENDING_ADMIN -> COMPLETED

Scenario B - rejet simple
- PENDING -> PENDING_ADMIN -> REJECTED
- meme transaction reutilisee

Scenario C - cooldown
- 3 rejets du cycle
- cooldown_until renseigne
- attente avant nouvel upload

Scenario D - expiration
- PENDING_ADMIN -> EXPIRED
- abonnement desactive
- remboursement requis

Scenario E - expiration remboursee
- EXPIRED + refund_done_at
- nouvelle transaction auto-creee

Scenario F - rejet apres validation
- transaction deja validee par le passe
- nouvelle preuve rejetee
- abonnement desactive
- transaction archivee
- nouveau TX ID cree au prochain chargement/initiate

17. Garde-fous de coherence
- ne jamais raisonner sur une vieille transaction au lieu de la derniere
- ne jamais creer de doublon PENDING pour un meme abonnement
- ne jamais ouvrir une nouvelle demande pendant un remboursement en attente
- ne jamais modifier une transaction historique archivee
- toujours reutiliser previous_provider lors d'un auto-remplacement
